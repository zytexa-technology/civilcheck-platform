# Pre-Production QA Audit — 2026-08-03

> **Status (2026-08-04):** all ten numbered findings below (#1–#10) have been fixed and pushed to `main`. This document is kept as-written as the historical record of what was found — see `docs/qa-fixes-status-2026-08-04.md` for current status in plain language, or the commit history on `main` from 2026-08-04 for the technical fixes themselves. The P2 list and the "what was checked and found solid" section are unaffected and still accurate.

Full-surface QA pass across all four workspace apps (`apps/api`, `apps/admin`, `apps/seller`, `apps/buyer`) ahead of a production launch decision. Scope: automated build/test/lint across every app, plus a manual security- and correctness-focused review of each app's source (auth/RBAC, IDOR, race conditions, payment integrity, dead/broken UI, cross-persona access). Every finding below was independently verified against the actual source — file:line citations are checked, not copied from a first pass.

**Bottom line: not production-ready as-is.** One finding (#1) is a full authentication bypass. Two more (#2, #3) are real authorization/session gaps. Everything else is fixable without architectural change. See `docs/roadmap.md` and `apps/admin/roadmap.md` / `apps/seller/roadmap.md` for the feature-completion history this audit builds on — this document only covers *new* findings, not the already-tracked "known, accepted limitations" those docs list (badge-gaming via one review, strike-fine ledger, seller-match ranking by locality only, GST inclusive/exclusive reading, the two disagreeing TDS rules — all still open product questions, unchanged by this audit).

## 🔴 P0 — Blocking. Do not launch with these unresolved.

### 1. Buyer and seller login OTP is a hardcoded static value with no production gate — full authentication bypass

**Where:** `apps/api/src/controllers/auth.controller.ts:31, 34, 48, 85, 394` (`sendOtp`, `verifyOtp`, `sellerVerifyOtp`, `sellerSendOtp`)

**What:** `const otp = '123456'` — there is no SMS provider call anywhere in this flow (confirmed: no Msg91/OTP-generation code exists in `src` for this path, despite Msg91 being fully integrated elsewhere for KYC/alert notifications — see `notification.service.ts`). Every other mock adapter in this codebase (`razorpay.ts`, `razorpayPayouts.ts`, `firebase.ts`, `cloudinary.ts`, `digilocker.ts`) explicitly checks `NODE_ENV === 'production'` and refuses to run its mock path — `auth.controller.ts` has no such check. `sendOtp` additionally echoes the OTP back in its JSON response.

**Failure scenario:** In production, anyone who knows (or scripts through) a registered phone number calls `POST /api/auth/verify-otp` or `POST /api/auth/seller/verify-otp` with `{"otp":"123456"}` and receives a valid 7-day JWT for that account. For a buyer: full access to purchase history, paid reports, personal data. For a seller: full access including the ability to change bank account/IFSC (see #4) and manage listings. This is scriptable at scale — every account uses the identical static code.

**Fix shape:** wire the existing Msg91 adapter into OTP send/verify (it already exists and is used elsewhere), and add the same `NODE_ENV === 'production'` refusal the other four adapters already use, so this can never silently ship live with the mock code path.

**Why this isn't just a "drop in credentials later" item:** the project's intended pattern — confirmed correct for Razorpay, RazorpayX, Firebase, Cloudinary, and DigiLocker — is blank env vars → mock mode → real credentials in `.env` → live, with zero code change needed, because each of those adapters reads its env vars at call time and refuses to run its mock path in production. OTP does not follow that pattern: it never reads any env var, so populating `MSG91_AUTH_KEY`/`MSG91_TEMPLATE_ID` would change nothing here. This is the one place in the codebase where "we're waiting on credentials" does not apply — it needs actual code, not just configuration, before it can ever become real.

### 2. Seller "partner role" (owner / expert / seller) is enforced only in the frontend UI, never on the backend

**Where:** `apps/api/src/middleware/auth.middleware.ts` (`sellerMiddleware`, ~line 163) — grep-confirmed: `partnerRole` is stored on the `Seller` model, returned in API responses (`seller.controller.ts`, `kyc.service.ts`), and used by `apps/seller`'s `Layout.jsx` to decide which nav tabs to render — but it is never read or checked by any Express middleware or route guard.

**What:** Every seller-scoped route (`listing.routes.ts`, `property-owner.routes.ts`, `earnings.routes.ts`, `specialRequest.routes.ts`, `seller.routes.ts`, `notification.routes.ts`) is gated only by `sellerMiddleware`, which checks the JWT and `kycStatus !== 'SUSPENDED'` — nothing persona-specific. Supporting evidence this isn't accidental-but-harmless: `sellerMatch.service.ts` documents that request auto-assignment "doesn't filter by profession — only ranks by locality and workload," and `specialRequest.controller.ts`'s `assignRequest` only checks `kycStatus === 'APPROVED'`, never `partnerRole`.

**Failure scenario:** Any authenticated seller's own JWT can be replayed directly (`curl -H "Authorization: Bearer $TOKEN" $API/api/seller/earnings`, or `POST /api/listing`, or self-accepting a special-request meant for an "expert") regardless of that seller's actual registered persona — an "owner" who never submitted a Bar Council certificate can act as a verification expert and get assigned/paid for that work. This doesn't leak *other sellers'* data (every controller correctly scopes by `sellerId`), so it's a persona-boundary bug rather than cross-tenant data leakage, but it is real backend-enforceable business logic currently living only in the React nav-rendering code.

**Fix shape:** add a `requireSellerRole('owner' | 'expert' | 'seller')` middleware (mirroring the admin app's existing `requireAdminRole`) and apply it to the routes that are persona-specific.

### 3. Admin "Sign Out" never invalidates the session server-side

**Where:** `apps/admin/src/context/AuthContext.jsx` (`logoutAdmin`) and `apps/admin/src/pages/Dashboard.jsx` (`handleLogout`)

**What:** Both only clear `localStorage` (`admin_token`, `admin_user`) and navigate to `/login`. The backend already has a real logout endpoint — `apps/api/src/controllers/auth.controller.ts`'s admin logout handler resets `Admin.lastActivityAt` (the actual server-side kill switch, since the 30-minute idle timeout in `auth.middleware.ts` is what really ends a session — the JWT itself is valid 7 days) and writes an `ADMIN_LOGOUT` audit entry. `apps/admin/src/api/auth.api.js` exports a `logout()` wrapper for exactly this endpoint, but grep confirms it is never imported or called anywhere in the app.

**Failure scenario:** a JWT copied out of localStorage (devtools, XSS, shared machine) before an admin clicks "Sign Out" remains fully valid against every `/api/admin/*` route after that click — clicking "Sign Out" is a purely client-side affordance with zero server-side effect. If that copied token keeps being used, `lastActivityAt` keeps refreshing and the session never expires on its own. Separately, the audit log (a compliance surface — `AuditLog.jsx`) will never show an `ADMIN_LOGOUT` entry for any admin, ever.

**Fix shape:** call the existing, unused `logout()` API wrapper from `handleLogout` before clearing local state and navigating.

## 🟠 P1 — Real issues. Fix before or immediately after launch.

**4. `PATCH /api/seller/profile` has no schema validation.** `apps/api/src/controllers/seller.controller.ts:441-484`, route at `seller.routes.ts:55`. Unlike registration (which validates the bank-account/IFSC pair via `sellerRegistrationSchema`), this endpoint accepts an unvalidated `bankAccount`/`ifsc` change with no confirmation step, no notification to the seller, and no audit-log entry (unlike every admin-side mutation). The following week's automated settlement run (`settlement.service.ts`) pays the seller's full pending balance to whatever account is on file. Combined with #1 (OTP bypass), this is a direct payout-hijack path today.

**5. `PUT /api/seller/listings/:id` has no schema validation.** `apps/api/src/controllers/listing.controller.ts:295-310` vs. `listing.routes.ts:22` (creation uses `listingCreateSchema` with `.min(99).max(4999)`, the update path does not). A seller can `PUT` a listing to any price, including negative, after it's been approved at a valid price — bypassing the platform's Rs 99–4999 cap. Re-review on update only recalculates `riskBadge`, not price bounds.

**6. Owner-submitted properties can skip every "mandatory" document.** `apps/seller/src/pages/owner/AddProperty.jsx` shows 8 documents marked mandatory with a red chip and `*`, but `submit()` only validates `title`/`area` before calling the API. The backend mirrors the gap: `apps/api/src/controllers/property-owner.controller.ts`'s `createProperty` accepts `documents: []` unconditionally and sets `status: 'PENDING'` regardless. Contrast with `apps/seller/src/pages/seller/NewListing.jsx`, whose step-gating actually blocks progression on missing required fields — this discipline didn't carry over to the newer, less-visited owner persona.

**7. Buyer app has no build-time safeguard against shipping with a `localhost` API URL.** `apps/buyer/src/config/env.ts:50-67` — `resolveBaseUrl()` falls through `EXPO_PUBLIC_API_URL` → Metro dev-host sniffing → `http://localhost:3000`. In a release build there's no Metro host, so an unset env var means the shipped app silently points at an unreachable `localhost` for every real device, with every screen stuck on an error state. The file already exports an `API_URL_IS_EXPLICIT` flag for exactly this purpose but it's never consumed anywhere — grep-confirmed the only reference is its own definition. There's also no `eas.json` in the repo defining per-build-profile env vars.

**8. Push notifications are fully unwired client-side in the buyer app despite complete backend FCM support.** `apps/buyer/src/api/alert.api.ts:52` exports `registerDeviceToken()` for `PUT /api/alerts/device-token`, but it's never called anywhere (grep-confirmed) and `expo-notifications` isn't even a listed dependency. `NotificationSettingsScreen.tsx:100-106` is self-aware of this ("This build does not yet register a device for push notifications") but the `pushEnabled` toggle above that notice still implies push is the thing being controlled. All alerts currently fall back to SMS/email regardless of buyer preference.

**9. A few 500 paths leak internal error detail to the client.** `apps/api/src/controllers/seller.controller.ts:104-115` (`sellerRegister`, returns raw Prisma error `code` like `P2002`/`P2022`) and `:270-275` (`digiLockerCallback`), plus `apps/api/src/controllers/notification.controller.ts:38-39, 56-57`. Not stack traces, but more internal detail than the rest of the codebase's error-handling convention exposes.

**10. Admin `createRefund` has a TOCTOU gap on its duplicate-refund check.** `apps/api/src/controllers/admin.controller.ts:1253-1307` — `findFirst` for an existing PENDING/PROCESSED refund, then `create`, with no transaction or unique constraint between the two. Two admins racing to submit a refund for the same `purchaseId` within milliseconds can both pass the check and create two PENDING rows. Money-safe (each is independently claimed by `executeRefund`'s own atomic `updateMany` guard, so no double-payout), but produces a duplicate ledger entry someone has to notice and clean up manually.

## 🟡 P2 — Minor, cosmetic, or process gaps

- **`apps/seller` has zero lint tooling** — no `eslint.config.js`, no `lint` script, unlike `apps/admin`. Recommend copying admin's config as a baseline; two of the P1 findings above (#6, and the race condition below) are exactly the class of thing a lint pass tends to surface attention near.
- **Admin JWT stored in plain `localStorage`** (`apps/admin/src/context/AuthContext.jsx`, `api/axios.js`). No XSS vector was found in this audit (`dangerouslySetInnerHTML`/`eval` grep came back empty), so this isn't exploitable today, but it means any future XSS — in this app or a shared subdomain — is a full session takeover. Worth a note for anyone evaluating hardening work later; not a blocker.
- **Firebase-SSO buyers aren't recognized by the purchase check on `GET /api/properties/:id`.** `apps/api/src/controllers/property.controller.ts:394-413` manually decodes the JWT and only checks `decoded.userId`, never validating a Firebase ID token the way `authMiddleware` does elsewhere — so a buyer who logged in via phone-OTP/Google/Apple SSO and already paid for a report still sees the locked free-preview version on this endpoint. Functional bug, not a security issue.
- **`apps/seller/src/pages/owner/MyProperties.jsx` has a stale-response race on rapid filter switching.** Its `load()` has no `live`-flag guard, unlike every sibling loader in the same app (`owner/Dashboard.jsx`, `owner/Analytics.jsx`). On a slow connection, switching filters quickly can let an older, narrower response overwrite a newer one, showing an incorrect empty state until the next state change.
- **Leftover fake trend data in the seller app's owner persona.** `owner/Dashboard.jsx` and `owner/Analytics.jsx` both hardcode `trend="▲ 8%"` / `trend="▲"` on stat cards — static strings, not derived from any real computation. The prior "remove fake data, fix dead UI" cleanup (see git history) appears to have missed this newer, less-visited persona.
- **`MyListings.jsx`'s "Earned" column is a client-side estimate, not the real ledger figure** — computed from `totalSales × price × currentBadgeCut` rather than summing actual `Purchase.sellerCut` rows, so it drifts if price or badge changed after a sale. Already honestly commented in the code as a stand-in; flagged here as a display-accuracy caveat, not a functional bug — real Settlements/Earnings figures elsewhere in the same app are ledger-accurate.
- **Minor dead code:** unused `Legend` import and an unused `createAuditLog()` API wrapper in `apps/admin`; dead `switchRole`/`addRole` no-op functions in `apps/seller`'s `AuthContext.jsx` (not reachable from any UI — leftover from an earlier multi-role design, not an exploitable privilege-escalation surface since nothing calls them).
- **No DigiLocker/Aadhaar KYC flow exists in the buyer app at all** (grep for `digilocker`/`aadhaar`/`kyc` in `apps/buyer` returns zero hits). Likely intentional — KYC is a seller-side concern per the product model — but worth an explicit product confirmation rather than an assumption.

## What was checked and found solid (worth knowing, not just what's broken)

- **Payment/webhook integrity:** Razorpay webhook raw body is preserved correctly (`express.raw()` mounted ahead of `express.json()` on the same path), HMAC-verified with `timingSafeEqual`, amount cross-checked against the frozen `PaymentOrder.amount`, and idempotent via an atomic `CREATED → PAID` claim. Checkout-verify endpoints correctly check order ownership before trusting a valid signature — no cross-user order hijack possible.
- **Race-safety on state transitions:** KYC decisions, listing approve/reject, spot-check strike escalation, refund execution, and weekly settlement all use `updateMany` with a status predicate as an atomic claim before acting — genuinely safe against concurrent admin clicks or concurrent settlement runs.
- **IDOR/ownership checks** are consistently applied across purchase certificate/invoice/flag/review, seller listing CRUD, owner-property CRUD, special-request endpoints, notification read, and alert cancel — every one compares the resource's owner FK against the authenticated principal.
- **SQL injection surface:** only two `$queryRaw` call sites exist (full-text search in `property.controller.ts`), both using Prisma's parameterized tagged-template form — no string interpolation.
- **Admin RBAC:** every route correctly scopes SUPER_ADMIN-only vs. SUB_ADMIN-eligible writes; no route found gated by the wrong tier. The frontend's `utils/permissions.js` mirrors this matrix and hides (not just disables) ungranted actions — real defense-in-depth on top of enforced backend RBAC.
- **Admin session/2FA:** 30-minute idle timeout enforced server-side, TOTP replay-window closed via `lastTotpStep`, 2FA-disable requires both password and a live code.
- **Rate limiting:** every sensitive route (OTP send/verify, admin login, admin 2FA, registration, payment/order creation) has a limiter mounted, keyed per-admin (not per-IP) for admin auth so a shared office IP can't lock everyone out.
- **Buyer app payment flow:** the "Pay" button only ever drives a dev-only mock checkout signed with a secret that cannot satisfy the real backend's HMAC check; the UI never marks a purchase "unlocked" on a client-side callback alone — it always awaits a server-verified round trip, and re-fetches the report from the server rather than trusting local state. When a live Razorpay key is configured, the mock path is explicitly disabled rather than silently continuing to run.
- **Buyer app token storage:** `expo-secure-store` exclusively, with a documented no-op (not a plaintext fallback) on web where SecureStore isn't available.
- **Buyer app deep linking:** the router's auth gate re-evaluates on every navigation regardless of entry path, so a deep link into an authenticated route can't bypass login.
- **Buyer app error handling / dead routes:** every data-fetching screen follows a consistent try/catch/finally pattern with retry affordances (no stuck-loading-forever paths found); every in-app navigation target resolves to a real route file.

## Methodology

Automated: `tsc --noEmit` + Jest for `apps/api`; `tsc --noEmit` + `eslint` for `apps/buyer`; `eslint` (both the correct pinned binary and, initially by mistake, the wrong hoisted one — see the lint-number note above) for `apps/admin`; an ad-hoc lint pass using `apps/admin`'s config for `apps/seller`, which has none of its own. Manual: four independent focused reviews (one per app) covering auth/RBAC, IDOR, race conditions, payment/webhook integrity, input validation coverage, dead/broken UI, and cross-persona access, with the most severe claims (the OTP bypass and the `partnerRole` gap) independently re-verified against the source directly rather than taken on trust.

No code was changed as part of this audit.
